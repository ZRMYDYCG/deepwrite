# 打包卡顿与超时诊断

遇到长时间无输出、测试超时或包内冒烟失败时读取。以下时间来自一次实际运行，用于帮助判断阶段，不是固定性能承诺。

## 全量测试静默数分钟

- **现象：**Vitest 输出 `RUN` 后几分钟没有新日志，绝大多数 worker 已退出，剩余一个进程仍在工作。
- **根源：**拆书规模测试会处理 300 章、3000 章和 300 万字，包含大量真实文件操作；完整测试曾耗时约 6–7 分钟。`scale.test.ts` 中部分用例允许 600 秒。
- **处理：**核对 `apps/desktop/src/utilities/long-book-decomposition/scale.test.ts` 的任务和超时，再检查本轮 Vitest 子进程的经过时间与 CPU。macOS 沙盒限制进程查询时，为必要的 `ps` 诊断申请沙盒外执行；不要据静默反复启动新测试。
- **边界：**CPU 活动只是仍在执行的线索。超过用例超时、持续无活动或出现错误时再收集栈、失败输出和子进程状态，定位死锁、未结束的子进程或实际性能问题。最终以测试总结与退出码验收。

## 文件集成测试超过默认 5 秒

- **现象：**全量运行中某项源文件或任务创建测试 5 秒超时；单独运行通过，之后同文件另一项又超时。
- **根源：**真实文件读写、原子保存和任务准备在并发负载下比单独运行慢。一次只放宽一个用例，然后立刻全量重跑，会反复碰到同类问题。
- **处理：**先读整份失败文件及其夹具，单独运行验证可观察行为和失败路径；必要时与相关磁盘测试一起运行，检查超时是否来自磁盘耗时、等待条件或清理缺失。只有证据支持耗时问题时，按该文件的实际操作统一设置合理超时，保留断言和清理。
- **已有实现：**`apps/desktop/src/extras/agents/sources/long-book-source-commands.test.ts` 使用 `vi.setConfig({ testTimeout: 30_000 })`；不是给所有测试统一提到 30 秒。相关检查通过后只重跑一次完整批次，不提前再单独执行全量 `verify`。

## Intel 冒烟等待菜单或整轮超时

- **现象：**ARM 冒烟通过，Intel 在 Rosetta 下首次启动偶尔通过，重新打开报 `Language smoke timed out: language menu closed`，或被外层 120 秒超时终止。
- **已验证因素：**冒烟窗口隐藏或使用 `showInactive()`，Electron 默认后台节流影响计时器和动画帧。语言选择菜单由 Vue 退场动画移除，脚本等待 DOM 消失可能超时；Rosetta 额外耗时使整轮更容易触及外层限制。
- **先检查：**查看 `package-smoke-runner.mjs` 的退出码、`signal`、`timedOut` 和应用输出。`DEEPWRITE_SMOKE_FAIL` 即使伴随 exit 0 也属于失败，不能只看退出码。再核对窗口是否节流、菜单是否已关闭、是否有本轮残留子进程；不能直接归咎于机器慢。
- **已有修复：**`apps/desktop/src/main/create-desktop-window.ts` 只在 `DEEPWRITE_SMOKE=1` 时设 `backgroundThrottling: false`，正常使用保持默认节流。该修复重建后，两种架构的首次启动与重新打开均通过。
- **恢复选择：**包内容未变且有环境诊断依据时只复验对应架构。修改窗口创建或 Main 内的冒烟代码属于包内容变化，需要重建受影响产物；不要把针对旧包的再次运行当成新代码验收。若节流已关闭仍失败，继续定位具体阶段，不能无限延长内外超时、关闭动画或跳过语言验证取得成功。

## 有失败后如何停止与续跑

- 尚未确认失败时，让有效测试完成；已确认失败且已找到修复后，可停止本轮 Vitest 主进程，让父级打包脚本接收失败并执行 `finally`，记录 `PACKAGE_RUNTIME_POSTCHECK_OK`。
- 用 PID、父子关系及临时冒烟路径确认进程归属；不要使用会匹配用户开发应用的广泛 `pkill Electron` / `pkill DeepWrite`。再次启动前检查本轮子进程和 DMG 挂载是否已清理。
- 硬中断或进程异常退出导致后置检查未执行时，单独执行 `pnpm electron:ensure`。路径、版本和可执行性检查通过只代表开发运行时可用，不代表完成了开发桌面运行验收。
- 下载、缓存或签名问题先有限诊断再重试。相同错误持续复现且没有新依据时，转向最小复现或说明外部阻塞，不重复整批构建。

## 三平台请求重复全量验证

- **现象：**分别执行 Mac ARM、Intel、Windows 打包，或者 Mac 打完再执行 Windows，每次入口都会重新跑完整 `verify`。
- **处理：**用 `pnpm pack:test:desktop`。该目标沿用 `tools/run-test-package.mjs`，选择两种 Mac 架构及 Windows x64，不包括 Linux；同一次编排只执行一次完整验证，Mac 两架构一起生成，最后统一恢复开发运行时。
- **限制：**入口目前没有持久化验证缓存或构建阶段续跑。不要杜撰开关、绕过检查裸跑 builder，也不要并发启动多个共享产物目录的批次。已有包的单独验收无需重建，源码变化后的构建仍执行完整编排。
